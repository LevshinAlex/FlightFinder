# Этап 1. Проверка источников авиаданных

Окончательный выбор API — до начала основной разработки (раздел 9 ТЗ).
Архитектура уже позволяет подключать поставщиков через `FlightProvider`
(`apps/api/src/providers`). Заполните таблицу по каждому кандидату.

| # | Требование | Skyscanner | Duffel | Travelpayouts |
|---|---|---|---|---|
| 1 | Коммерческий API доступен | партнёрское одобрение | да, self-serve | да, партнёрская программа |
| 2 | Вылеты из TLV | ☐ проверить | ☐ проверить | ☐ проверить |
| 3 | Поиск по стране назначения | ☐ (indicative, entity страны) | нет — по аэропортам | нет — по городам/аэропортам |
| 4 | Фильтр пересадок | ☐ | да (`max_connections`) | данные о пересадках есть |
| 5 | Полная цена туда-обратно | ☐ | да (`total_amount`, все пассажиры) | цена за 1 взрослого из кэша |
| 6 | Ссылки на бронирование | ☐ (redirect) | нет (продажа через API) | да (aviasales + marker) |
| 7 | Лимиты и стоимость запросов | ☐ | плата за превышение search-to-book | ☐ |
| 8 | Разрешено хранить историю цен | ☐ | ☐ | ☐ |
| 9 | Требования к переходам/бронированиям | ☐ | ☐ | ☐ |

## Прототип для проверки (рекомендация ТЗ)

1 маршрут (TLV → Италия), 9 комбинаций дат, все аэропорты страны:

```bash
# в .env: INDICATIVE_PROVIDER=travelpayouts  LIVE_PROVIDER=duffel  (+ ключи)
npm run dev:api & npm run dev:worker
# создать мониторинг в UI и посмотреть результаты / логи worker'а
```

Метрики для оценки: число вызовов API на мониторинг (`SearchRun.combinationsChecked`),
доля кэш-попаданий (`DailyBatch.cacheHits`), расхождение indicative vs live цен,
доля пропущенных indicative-кэшем комбинаций.

## Оценка объёма запросов

500 пользователей × 3 направления × 9 комбинаций × ~10 аэропортов ≈ 135 000 indicative-ключей в день
(до дедупликации), но live-проверок — только top-N (по умолчанию 10 + по одной на аэропорт) на мониторинг.
Параметры: `LIVE_CHECK_TOP_N`, `PROVIDER_CONCURRENCY`, `SEARCH_CACHE_TTL_MINUTES`.
