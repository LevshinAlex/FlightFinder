# ✈️ Flight Price Tracker (FlightFinder)

Веб-сервис автоматического мониторинга цен на авиабилеты: пользователь один раз настраивает
поездку, система каждое утро проверяет цены, хранит историю, считает тренды и присылает сводку.

> *Configure once. Track automatically. Buy at the right price.*

## Быстрый старт (Docker)

```bash
cp .env.example .env
docker compose up --build
```

Откройте http://localhost:3000. По умолчанию работает **mock-поставщик** (демо-цены, не настоящие).

## Локальная разработка

Нужны Node.js 20+, PostgreSQL 14+ и Redis 6+ (можно поднять только их: `docker compose up postgres redis`).

```bash
npm install
cp .env.example .env
npm run db:migrate          # создать схему БД
npm run db:seed             # демо-пользователь demo@example.com / demo12345
npm run dev:api             # API  → http://localhost:4000/api
npm run dev:worker          # планировщик + очереди
npm run dev:web             # сайт → http://localhost:3000
```

Заполнить демо-историю цен за N дней (только mock, **удаляет** текущую историю активных мониторингов):

```bash
npm run demo:history -w apps/api -- 21
```

Тесты:

```bash
npm test
```

## Как это работает

1. **Планировщик** (worker, каждые 5 минут) находит пользователей, у которых до времени отчёта
   (по умолчанию 07:00 Asia/Jerusalem) остался час, и ставит в очередь один пакет поиска.
2. **Поисковый движок** для каждого мониторинга строит комбинации дат (10.05 +2 / 20.05 −2 → 9)
   × все аэропорты страны и выполняет **двухэтапный поиск**:
   - этап 1 — предварительные цены (indicative) по всем комбинациям;
   - этап 2 — актуальная проверка (live) только top-N самых дешёвых + по одной комбинации
     на каждый аэропорт (контроль неполноты кэша).
   Одинаковые запросы разных пользователей **группируются** и **кэшируются** в Redis.
3. Результаты фильтруются (пересадки — **в каждую сторону**, self-transfer исключены),
   сохраняются (`FlightOffer`, `PriceSnapshot`) и анализируются.
4. Когда поиски пользователя завершены (или прошло 45 мин после времени отчёта) — отправляется
   **одно письмо** со сводкой по всем активным мониторингам. При значительном снижении цены
   или достижении цели — дополнительный алерт.

### Важные правила данных
- Статусы запуска: `SUCCESS`, `PARTIAL`, `NO_RESULTS` (поставщик ответил, рейсов нет) и `FAILED`
  (поставщик недоступен). При `FAILED` пользователю **не** сообщается ни «цена выросла», ни «рейсов нет».
- Каждая цена имеет статус `LIVE` (подтверждена) или `INDICATIVE` (предварительная) и время проверки;
  предварительные цены явно помечаются в интерфейсе и письмах.
- Сравниваются два показателя: изменение самого дешёвого варианта по стране и изменение
  **того же** маршрута/дат. Смена города (Милан → Рим) показывается отдельно.
- Отсутствующие у поставщика функции бросают `ProviderNotSupportedError`, а не имитируются.
- Circuit breaker: при серии отказов поставщика оставшиеся запросы прекращаются.

| `PROVIDER_DAILY_PACING` | `true` — квота делится на оставшиеся дни месяца |

### Несколько источников

Не полагаемся на один источник — каждый этап принимает список в порядке приоритета:

```env
INDICATIVE_PROVIDER=travelpayouts,ignav   # Ignav дозаполняет комбинации без цены в кэше Travelpayouts
LIVE_PROVIDER=ignav,serpapi               # SerpApi — только если Ignav недоступен
CONTROL_PROVIDER=serpapi                  # независимая перепроверка самого дешёвого варианта
```

- **Предварительные цены — дозаполнение.** Следующий поставщик запрашивается только для пар
  «аэропорт + даты», по которым у предыдущих нет подходящей цены.
- **Live — резерв.** Следующий поставщик используется только при сбое или неподдерживаемом
  запросе. Пустой ответ — это настоящий ответ (`NO_RESULTS`), его не перепроверяем.
- **Контроль.** Самый дешёвый live-вариант каждого мониторинга перепроверяется в
  `CONTROL_PROVIDER`. Результат (`primaryPrice`, `controlPrice`, `diffPct`) сохраняется в
  `SearchRun.analysis.control`. Если контрольный источник нашёл тот же маршрут дешевле, эта цена
  попадает в результаты. Сбой контроля не влияет на статус запуска.
- **`ignav` как источник предварительных цен** использует поиск дешёвых дат: один запрос на
  длину поездки покрывает до 31 даты вылета. В ответе нет рейсов и пересадок, поэтому такие цены
  только выбирают, что проверять на втором этапе, и не сохраняются. Нужен `LIVE_PROVIDER`.

Бесплатные live-поставщики (`serpapi`, `ignav`, `hasdata`) подходят для прототипа и проверки,
но не для ежедневной работы: один мониторинг — это до `LIVE_CHECK_TOP_N` + по одной проверке
на аэропорт в день. Для них уменьшите `LIVE_CHECK_TOP_N` (например, до 2–3).

- **SerpApi / HasData** — цены Google Flights на момент запроса. Обратный рейс в Google
  запрашивается отдельно, поэтому одна live-проверка = **2 запроса**, и проверяется только самый
  дешёвый вылет туда. HasData не документирует значения `stops`/`travelClass`: пересадки
  фильтруются по реальным сегментам, поддерживается только эконом.
- **Ignav** — туда-обратно одним запросом. Валюты в запросе нет: цены приходят в валюте рынка
  `IGNAV_MARKET` (по умолчанию `IL`, ₪) и пересчитываются в USD. Цена со статусом `verified` →
  `LIVE`, иначе `INDICATIVE`.
- **Kiwi (RapidAPI)** — неофициальная обёртка над kiwi.com: туда-обратно одним запросом, оба
  направления с сегментами. Фильтра пересадок в этом запросе нет — фильтруем сами. Пересадка с
  повторной регистрацией багажа считается self-transfer и исключается. Перед использованием
  проверьте probe-скриптом, что цена — за всех пассажиров.
- **Skyscanner Scraper (RapidAPI, OmkarCloud)** — самая большая бесплатная квота (1000/мес): туда-обратно
  одним запросом, сегменты, номера рейсов, ссылки агентов, признак self-transfer. Ответ ~11 с (скрейпер
  опрашивает Skyscanner). Рынок продажи — `SKYSCANNER_MARKET` (по умолчанию `IL`).
- **FlightPowers (RapidAPI)** — цены Google Flights: пары туда-обратно одним запросом, пересадки
  по каждому направлению, ссылка Google Flights и оценка цены Google. Сегментов и номеров рейсов
  нет — в интерфейсе вместо времени показываются даты. Признака self-transfer тоже нет.

### Бесплатные квоты

У бесплатных тарифов 20–300 запросов в месяц, поэтому каждый запрос к поставщику учитывается
(`src/providers/budget.ts`, счётчики в Redis — общие для API и воркеров):

- **Месячный лимит** в единицах поставщика: поиски SerpApi, кредиты HasData (15 за запрос),
  запросы RapidAPI. Запрос сверх лимита не отправляется — цепочка переходит к следующему поставщику.
- **Дневная доля:** за день можно потратить (остаток месяца) / (оставшиеся дни), чтобы квоты хватило на весь месяц.
- **Ответ поставщика важнее нашего счёта:** «квота исчерпана» ставит поставщика на паузу до сброса,
  а заголовки RapidAPI `x-ratelimit-requests-*` обновляют счётчик.
- **Планирование:** движок заранее считает, сколько live-проверок ещё помещается сегодня, и
  распределяет их по кругу — сначала лучший кандидат каждого мониторинга. Ответы из кэша квоту не тратят.
  Если на мониторинг не осталось ни одной проверки, запуск завершается с сообщением о квоте,
  а не «поставщик недоступен».
- Остатки квот видны в `GET /admin/status` (`quotas`).

### Валюта: всё в долларах США

Все цены хранятся, сравниваются и показываются в `BASE_CURRENCY` (USD). Цены поставщиков в
другой валюте пересчитываются по курсу дня (Frankfurter, без ключа); исходная цена сохраняется
(`FlightOffer.originalPrice/originalCurrency`) и видна в интерфейсе. Существующие мониторинги
при старте API переводятся в USD: желаемая цена пересчитывается по текущему курсу, сравнение цен
начинается заново (старые цены — в другой валюте).

### Оценка цены от Google

SerpApi, HasData и FlightPowers возвращают вместе с ценами оценку Google: `low` / `typical` / `high`, обычный
диапазон цен и историю цен по маршруту. Это показывается на странице мониторинга, история —
пунктиром на графике (у нового мониторинга график есть с первого дня). Переход в оценку `low`
даёт алерт. Алерты отправляются только по live-цене — цена из кэша могла уже исчезнуть.

Skyscanner — заготовка адаптера до получения партнёрского доступа. Перед выбором поставщика
пройдите чек-лист в [docs/PROVIDER_EVALUATION.md](docs/PROVIDER_EVALUATION.md).

## Критерии приёмки (раздел 15 ТЗ)

| № | Проверка | Где |
|---|---|---|
| 1 | 9 комбинаций дат | `test/acceptance.spec.ts` |
| 2 | Несколько аэропортов страны | тест + справочник |
| 3 | Пересадки в каждую сторону | тест `filterOffers` |
| 4 | История после нескольких запусков | экран мониторинга, `demo:history` |
| 5 | ₪1000 → ₪900 = −10% | тест `analyzePrices` |
| 6 | Одно письмо со всеми мониторингами | тест `buildDailyReport`, `NotificationService` |
| 7 | Пауза останавливает поиск и уведомления | фильтр `status: ACTIVE` в планировщике/движке/отчёте |
| 8 | Сбой API ≠ «цена выросла»/«рейсов нет» | тест + статус `FAILED` |
| 9 | Изоляция пользователей | все запросы с `userId` (чужой id → 404) |
| 10 | Время проверки и статус достоверности | `observedAt`, `priceStatus` |

## Справочник аэропортов

`apps/api/src/airports/data/countries.json` содержит ~150 аэропортов 38 популярных стран.
Для полного справочника его можно сгенерировать из открытого набора OurAirports
(аэропорты типа large/medium с регулярными рейсами и кодом IATA).

## Ограничение

Система показывает минимальную цену среди доступных ей предложений, но не гарантирует
абсолютную минимальную цену на всём рынке.
